# PawPal+ Project Reflection

## 1. System Design

**a. Initial design**

The initial design has four classes. One for an owner and pet's information (such as name or type), each Pet
has a list of care Tasks, and a Scheduler takes the Owner's information and builds a daily plan. The three core actions are adding a pet, adding/editing a care task, and generating today's plan.

- **Owner**: stores the owner's name, their list of pets, and constraints such as how many minutes they have available each day and any preferences. Responsible for adding pets and exposing their tasks to the scheduler.
- **Pet**: stores the pet's name, species, and age, plus its list of tasks. Responsible for adding and removing tasks for that pet.
- **Task**: stores a title (walk, feeding, meds, etc.)duration, priority, and whether it is completed. Responsible for representing one care activity and its details.
- **Scheduler**: takes the owner's pets and tasks and the time available. Responsible for choosing and ordering tasks by priority so they fit within the time limit, and for producing a short explanation of why each task was included or left out.

**b. Design changes**

- Did your design change during implementation?
- If yes, describe at least one change and why you made it.

Yes, I made two small changes to my skeleton after reviewing it.

First, I replaced `pass` with `raise NotImplementedError` in all the method stubs. With `pass`, an unfinished method silently returns `None`, which could cause confusing errors later (for example, trying to loop over the result of
`generate_plan()`). Raising `NotImplementedError` makes it clear which method has not been built yet.

For example
Before (generated by my AI assistant):
```python
def remove_task(self, task: Task) -> None:
    pass
```

After:
```python
def remove_task(self, task: Task) -> None:
    raise NotImplementedError
```

Second, I changed `Task.edit()` to accept parameters (`edit(**changes)`). The original `edit()` took no arguments, so there was no way to say which fields should change. With `**changes`, I can call something like `task.edit(duration_minutes=45, priority="high")`.

For example
Before:
```python
def edit(self) -> None:
    pass
```

After:
```python
def edit(self, **changes) -> None:
    raise NotImplementedError
```

## 2. Scheduling Logic and Tradeoffs

**a. Constraints and priorities**

- What constraints does your scheduler consider (for example: time, priority, preferences)?
- How did you decide which constraints mattered most?

My scheduler considers four things: the owner's available time, task priority, whether a task is already completed, and overlapping start times.

Available time is a hard limit, so the plan never uses more minutes than the owner has. Within that limit, tasks are ordered by priority (high, medium, low), and shorter tasks go first when priorities match. Completed tasks are skipped, and tasks whose fixed times overlap are left out and reported as conflicts. The owner's preferences are stored but not used by the scheduler yet.

I decided that time and priority mattered most because they come straight from the README scenario, and because they decide what happens when the day is too full: the important tasks, like medication and feeding, should be kept and low-priority ones like play time should be dropped first. Conflicts came next, because one owner cannot do two tasks at the same time, even for different pets.

**b. Tradeoffs**

- Describe one tradeoff your scheduler makes.
- Why is that tradeoff reasonable for this scenario?

My scheduler uses the simple pairwise check to detect conflicts instead of a faster sweep-line method. It is slower for large task lists, but it is easier to read, and a single household has few tasks.

**b. Tradeoffs**

My scheduler detects conflicts and reports them, but does not resolve them.
When two timed tasks overlap, `generate_plan()` leaves both out of the plan
instead of keeping the higher-priority one, and `get_conflict_warnings()`
only tells the owner about the clash. This is a tradeoff because a real
owner would probably want the more important task kept, for example
medication over play time.

I kept it this way because it is simple and predictable: the owner sees a
warning and decides which task to move, and the scheduler never silently
chooses between two fixed-time tasks. It is also reasonable because one
owner cannot do two tasks at once, even for different pets, so any overlap
is a real problem that needs a human decision.

A second, smaller tradeoff: conflicts are found by comparing every pair of
tasks. That is slower than a sweep-line approach for very long lists, but
a household has few tasks, and the simple version is easier to read and test.

## 3. AI Collaboration

**a. How you used AI**

- How did you use AI tools during this project (for example: design brainstorming, debugging, refactoring)?
- What kinds of prompts or questions were most helpful?

Initially, I used Claude to break down the concept of what we're gonna do today. Then, I used AI for checking my workflow and logic I proposed. For example, when my AI assistant suggested me to add 'pass' instead of using 'NotImplementedError' in pawpal_system.py. 'pass' makes the methods silently return None, which can hide bugs.

For me, it's on Part 2: "Based on my skeletons in pawpal_system.py, how should the Scheduler retrieve all tasks from the Owner's pets?" My AI assistant inside VSCode helps me to add more info on what should I need to make owners easy to navigate their pets' schedule

The most effective features were having the assistant read my files directly and edit several files at once, such as adding recurrence, which touched `Task`, `Scheduler`, and the tests. Chat with files attached worked best for reviews: "what is missing from this skeleton?" and "how could this method be
simplified?" gave concrete, checkable answers. I used separate chat sessions for planning algorithms and for planning tests. That kept each conversation focused, and I could compare each assistant's answer with my own notes without earlier implementation details getting in the way.

**b. Judgment and verification**

- Describe one moment where you did not accept an AI suggestion as-is.
- How did you evaluate or verify what the AI suggested?

When I asked my AI assistant to suggest algorithm improvements, it offered a simple and a "more efficient" version of each feature (for example, a sweep-line conflict check instead of comparing every pair of tasks). I did not take the more efficient versions. A household has maybe 10 to 20 tasks, so the speed difference would not be noticeable, and the simple code is easier to read and test.

For recurring tasks, the assistant pointed out that a single `completed` flag cannot tell "done today" from "done forever". Its fixes (dated occurrences with separate completion status) were more than I needed, so I plan to create the next occurrence when a daily or weekly task is completed.

I also decided that overlaps across different pets still count as conflicts, since one owner has to do all the tasks. I will check these choices by writing tests for each behavior, not just by reading the output.

I asked my AI assistant for a lightweight conflict detection method. It
found that a version already existed and tightened it instead of adding a
duplicate: same-pet overlaps are now identified by pet object rather than
name, and invalid or non-string start times return a warning instead of
raising an error. I reviewed the diff, checked that the new tests did not
duplicate mine, and confirmed the test suite and main.py demo still ran.

I asked my AI assistant how `get_conflict_warnings()` could be simplified.
It suggested replacing the slice in the pair loop with index-based loops,
extracting the invalid-time check into a helper, and caching parsed times.
I rejected the index loops because they were harder to read than the
original, and I rejected caching because it would change `_tasks_overlap()`,
which other methods depend on, for a speed gain that doesn't matter with a
household's few tasks. I used `itertools.combinations` instead, which
removes the slicing and reads more clearly. I verified the change by
running the tests and `main.py`, and the output was identical.

While planning tests, I found that `sort_by_time()` compared start times as
strings, so "9:00" would sort after "18:00". I fixed it by sorting on minutes

**b. Confidence**

- How confident are you that your scheduler works correctly?
- What edge cases would you test next if you had more time?

I'm fairly confident (4 out of 5) that the scheduler works correctly. All 21
tests pass, and they cover edge cases as well as normal use: identical and
overlapping start times, back-to-back tasks, invalid times, recurring tasks
completed twice, and tomorrow's copy of a task staying out of today's plan.

Edge cases I would test next: unknown priority values like "urgent", zero
available minutes, a task fully contained inside another task's time slot,
and owners with no pets. I also haven't tested the Streamlit UI automatically.

## 5. Reflection

**a. What went well**

- What part of this project are you most satisfied with?
I'm most satisfied with building the system in layers. I designed the UML,
wrote a skeleton, implemented the logic, and checked it with a CLI demo and
tests before touching the Streamlit UI. Because the backend was already
verified, connecting it to the UI was straightforward. I'm also happy with
the recurring-task feature, which creates the next occurrence with
`timedelta` and keeps it out of today's plan until it is due.

**b. What you would improve**

- If you had another iteration, what would you improve or redesign?
I would let tasks know which pet they belong to, for example with a
`pet_name` field. Right now `main.py` and the UI have to rebuild that link
by hand. I would also resolve conflicts instead of only reporting them, so
the higher-priority task stays in the plan. Finally, I would use the
owner's `preferences`, which are stored but not used yet, and replace the
string priorities with an Enum so unknown values can't slip in.

**c. Key takeaway**

- What is one important thing you learned about designing systems or working with AI on this project?

Being the lead architect meant deciding what the system should do and treating the AI as a fast collaborator that proposes options. It could produce code quickly, but it did not know my priorities: it offered sweep-line conflict detection and per-date completion tracking, which were more than a household scheduler needs. I rejected those, kept the simple
pairwise check, and used `itertools.combinations` only because it made the code easier to read. Each time, I ran the tests and the demo to verify the result. My main lesson is that clear design decisions made before coding (UML, then skeleton, then tests) let me judge AI output instead of just accepting it.
